# 设计原则

以下均为【建议】，是 v0.1 的研究工作规则，不是已证明的普遍最优架构。

| 原则 | 实际含义 | 必须保留的边界 |
|---|---|---|
| 知识 DRY，实现允许 WET | DRY 指知识有一个明确权威来源；WET 在此指允许局部重复实现，不要求固定份数 | 权威来源可以分布存储；必须有版本、来源和冲突处理。共享库仍可采用，尤其在验证充分时 |
| 状态持久，实现可临时 | 事实、身份、权限、规则和证据不只存在于某份代码或对话 | 临时不等于立即删除；保留已采用实现及必要失败样本，支持审计和重放 |
| 试错前置，提交严格 | 先在隔离环境验证候选，再改变正式状态 | “提交”指写入业务状态或造成外部效果，不只是 Git 保存代码；未知即不自动放行 |
| 目标可检验，过程允许变化 | 定义合格结果集合与资源预算，允许不同路径 | 有评分不等于规格完整；明确“无法判断”出口 |
| 生成与验收分离 | 生成者的解释不能充当运行证据；测试来源和检查机制尽量互补 | 不把多个实现的一致意见视为正确性证明 |
| 保留契约，允许生成适配器 | 契约是接口双方必须遵守的数据和行为约定；适配器负责格式转换 | 单位、权限、时间语义、失败语义都须检查 |
| 反馈控制服务于明确目标 | 观察偏差，选择修补、替换、回滚、降级或停机 | 延迟、成本等软目标只能在硬约束内优化 |
| 把历史经验写回环境 | 特例记录来源、范围、生效时间、失效条件和检查方法 | 规则变化要评审；不能因某候选失败便自动降低验收标准 |
| 为注意力和计算设预算 | 限制候选数、重试次数、运行时间和人工升级频率 | 达到预算后保留失败现场并停止或升级，不能无期限生成 |

## 一个示例

【建议】一个报表单元只读取授权数据，按规则版本 R2 生成图表。可生成多个实现，用固定边界案例和独立数据核对。展示效果可评分，但越权读取属于直接拒绝项。新实现采用后仍记录规则版本、输入摘要、测试证据和实现编号。

【不确定】局部重复是否优于共享库、重新生成是否优于修补，都依赖实际成本；由 [三份提案](../提案-RFCs/0001-知识DRY实现WET-Knowledge-DRY-Code-WET.zh-CN.md) 和 [EX-08](../实验-Experiments/08-持续演进对照实验-Longitudinal-Comparison.zh-CN.md) 检验。术语解释见 [术语表](术语表-Glossary.zh-CN.md)。
