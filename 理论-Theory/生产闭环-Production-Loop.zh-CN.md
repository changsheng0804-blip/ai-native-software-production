# 生产闭环

【建议】闭环的长期产物包括工作单元、可检查的约束、执行证据、持久知识和可追溯的决策。以下是待实验的参考流程。

~~~mermaid
flowchart TD
  A["人：目标、边界、取舍"] --> B["环境：事实、规则、权限、证据"]
  B --> C["分解任务，确定契约和预算"]
  C --> D["生成候选"]
  D --> E["隔离执行，独立验收"]
  E --> F{"硬约束合格且证据足够？"}
  F -->|"否／无法判断"| G["修补、重生、放弃或人工判断"]
  G --> C
  F -->|"是"| H["组合检查，核对最新状态"]
  H --> I["受控提交与采用"]
  I --> J["运行观察"]
  J --> K["复核后更新知识"]
  K --> B
  J --> G
~~~

## 每一步留下什么

| 步骤 | 必须留下的对象 | 主要责任 |
|---|---|---|
| 目标与边界 | 合格行为、禁止行为、软目标、资源上限、升级条件 | 人定义取舍；工具辅助表达 |
| 任务分解 | 单元编号、输入输出、依赖、所需规则版本 | 系统提出，人处理冲突或无法分解的部分 |
| 候选生成 | 实现编号、生成配置、输入和知识版本 | 生成环节 |
| 隔离验收 | 测试版本、原始结果、失败样本、未知项 | 验收环节，使用互补证据 |
| 组合与提交 | 全局约束检查、当前状态版本、采用理由 | 提交控制机制 |
| 运行观察 | 行为、异常、成本、受影响范围 | 运行环境 |
| 经验沉淀 | 事件来源、修订规则、范围、失效条件 | 评审后纳入知识 |

## 提交边界

【建议】候选只能提出变更计划；正式写入由明确的提交机制执行。该机制核对身份、权限、规则版本、当前状态、硬约束和操作唯一编号。硬约束未通过、验收冲突、快照过期或预算用尽时停止自动提交。

对于会竞争同一状态的操作，检查和写入必须有并发控制，不能“先检查，过一会直接写”。数据库隔离的具体行为已有文档说明，但跨系统效果仍需另行设计。[E04](../证据-Evidence/证据与参考-Evidence-and-References.zh-CN.md#e04)

## 失败后的决策

【建议】实现局部缺陷可修补；规则明确且替换成本低时可重生；新版本破坏行为时考虑回滚；依赖不可用时降级；规格冲突、越界或验收无法判断时交给人。回滚代码不自动撤销已发送的消息或其他外部效果，应记录待核对事项。

## 让下一轮继承历史

【建议】每条新知识至少包含“编号、命题、来源事件、适用范围、版本、失效条件、验证方式、当前四类状态”。撤销旧规则时保留替代关系，不把错误结论从历史中抹去。

【不确定】验收器和知识本身也可能错。闭环要检验它们如何被发现、质疑和修正。[开放问题](开放问题-Open-Questions.zh-CN.md)
