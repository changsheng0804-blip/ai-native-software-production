# RFC-0004：瞬时视觉表层与意图反推

认识状态：【建议 / Proposal】<br>
提案流程：草案 / Draft<br>
关联命题：H2（持久状态与临时实现）、H4（接口刚性连续谱）；问题：Q1（无线性接口的功能实现）、Q3（验证成本）；实验：EX-08 的交互层扩展

## 问题与假设

【推断】传统图形用户界面（GUI）依赖漫长而刚性的实现管线（数据库 → 后端 API → 状态管理 → 组件树 → 样式系统 → DOM 渲染），导致大量边缘视图与临时交互代码成为系统的维护负担（在多数商业软件中占比可达 60%–80%）。

如果将界面视为“持久语义状态的瞬时投影”，取消静态前端代码库，由生成引擎按需即时合成视觉呈现，并通过视觉定位（Visual Grounding）将用户交互反推为确定性业务意图，是否能在不牺牲数据真实性的前提下，彻底消除前端实现的维护债务？

## 提议

【建议】建立“双层交互解耦模型”：

| 层级 | 资产形态 | 生命周期与特征 |
|---|---|---|
| 底层：持久事实与不变量 | 数据库记录、用户身份、账户余额、业务断言（如总额守恒、权限控制） | 长期持久存在，严格确定性，只接受经过校验的状态变更 |
| 表层：瞬时视觉表层 | 由生成模型即时合成的视觉产物（临时 HTML/Tailwind、SVG 或多模态图像） | 瞬时（单次会话或交互后即销毁），无静态代码库，不承担持久事实存储 |

交互闭环包含四步：
1. **状态投影**：生成引擎读取底层持久状态，直接合成针对当前意图与上下文的视觉表层（例如 Flipbook 式的整页连续流或轻量瞬时 HTML）。
2. **操作捕获**：捕获用户在视觉表层上的原始交互信号（如屏幕坐标、点击区域、语音或自然语言输入），而非依赖预编译绑定的固定控件事件监听器。
3. **意图反推（Grounding）**：多模态模型结合当前视觉上下文与坐标，反推结构化业务意图（如“用户点击了确认购买单号为 #1024 的红外套”）。
4. **守门提交**：意图经由 RFC-0003 定义的提交门禁，由确定性规则检查硬不变量；合规后写入底层数据库，并触发下一轮视觉表层投影。

## 适用边界与重写安全区

【建议】本机制及其底层的“抛弃旧实现直接重写”策略，绝不能滥用于系统所有环节，必须严格满足以下三项物理特征：

1. **计算自足（无外部不可逆副作用）**：交互与数据处理过程在沙箱内纯闭环完成。涉及真实外部世界物理操作（银行扣款发往外部通道、群发短信、硬件执行等）必须在最终状态提交后由确定性网关触发，严禁在试探性表层中试错。
2. **验证不对称性（NP 特征）**：生成视觉或处理代码可能需要复杂推理，但验证其是否合规必须在毫秒级内由机器确定性完成（如检查总计金额是否守恒、行数是否一致）。
3. **低逆向成本（随时可撤销重试）**：生成失败或被不变量拦截时，由于不产生状态残留，可零代价打回重新生成。

## 最小验证设计

【建议】设计一个微型业务场景（如：动态报表分析看板，或含有优惠满减的简易商品结算）：
- A 组（传统 GUI）：编写标准的后端 REST API、React 前端组件库、状态管理及样式文件；每次遇到格式变更或临时筛选需求，由 Agent 修补既有前端代码。
- B 组（瞬时视觉表层）：仅保留底层 SQLite 数据库与断言检查器；前端由模型根据数据即时生成无依赖单页或 Canvas 投影，用户交互通过坐标与意图解析写入数据库。

连续注入 30 次布局改变、特例过滤条件与异常输入，记录：
- 代码库膨胀行数与技术债务留存量；
- 回归 Bug 数量（新需求是否破坏了旧界面的显示与校验）；
- 人类维护与审查总耗时。

## 判断和停止

【建议】若 B 组由于多模态意图反推的歧义性，导致硬不变量拦截率过高、重试延迟严重影响用户可用性（如单次交互等待 > 3 秒），或出现无法容忍的交互识别漂移，应停止推进完全无接口化，退回至“可生成轻量结构化契约”的中间形态。
