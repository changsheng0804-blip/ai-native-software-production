# RFC-0002：状态持久，实现可临时

认识状态：【建议 / Proposal】<br>
提案流程：草案 / Draft<br>
关联命题：H3、H5；问题：Q4；实验：EX-08 的继承与恢复检查

## 问题与假设

【推断】如果业务知识或运行状态只藏在实现和某次对话里，替换实现可能丢失历史。把它们显式保存，可能使修补、替换和重新生成都更容易。

## 提议

【建议】区分三类资产：

| 资产 | 最少内容 | 寿命与处理 |
|---|---|---|
| 事实与状态 | 用户数据、对象身份、状态版本、事件与操作编号 | 按业务与保留规则持久保存 |
| 知识与约束 | 规则、例外、权限、验收器、来源、适用范围 | 显式版本化；修订时保留历史 |
| 实现与运行证据 | 代码或制品、配置、输入摘要、验证记录、采用与替代关系 | 实现允许替换；采用过的版本和必要证据按策略留存 |

长期资产不等于永远不变，也不等于无限期保留个人数据。实现寿命按成本、需求与可追溯性决定；不预设“30 秒销毁”或“毫秒生成”。

## 替换协议

【建议】准备一个低副作用的报表或格式转换单元，依次：

1. 记录当前单元身份、实现版本、规则版本和状态结构。
2. 在隔离副本生成替代实现；读取显式知识，不能靠旧对话补充隐藏特例。
3. 检查历史案例、当前状态、兼容性、权限与未完成操作。
4. 若数据结构改变，单独验证迁移与恢复办法；检查读写并发和旧版本兼容。
5. 采用时记录生效点和替代关系；验证运行行为并保留恢复路径。

切换实现与迁移数据是不同操作。回退实现能否继续读取已迁移数据，必须单独检查；不可逆外部效果另做核对与补偿设计。

## 对照与观测

【建议】两个组使用同样显式知识和状态边界：A 修补原实现，B 允许整单元重新生成。用固定序列加入新规则、旧版本例外、运行中断、重复请求和一次状态结构变化。另做“保留对话／全新会话”的对照，分离知识外置的作用。

记录历史验收保留率、状态核对差异、恢复时间、重复执行次数、人工补充隐藏知识的次数、全部迁移和保存成本。生成配置应作为复现参数保存，不用模型身份组织研究观点。

## 判断和停止

【建议】任何事实丢失、权限越界、同一操作重复生效都记为失败并暂停该路径。必须计入恢复成本。规则和历史行为保持合格后，才比较时间与总成本。

【不确定】如果 B 需要大量迁移或人工解释，结论可能只是“知识外置有帮助”，而不是“重新生成优于修补”。不要求所有代码短命；确定性的稳定核心仍可长期保留。
