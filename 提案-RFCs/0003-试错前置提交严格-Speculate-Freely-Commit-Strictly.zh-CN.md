# RFC-0003：试错前置，提交严格

认识状态：【建议 / Proposal】<br>
提案流程：草案 / Draft<br>
关联命题：H4；问题：Q2、Q3、Q8；实验：EX-08 的副作用与并发检查

## 问题与假设

【推断】在可控环境内尝试多个方案，可能以更多计算换取更少的真实错误。收益取决于模拟覆盖度、状态新鲜度、验收能力和提交成本。

## 提议

【建议】建立明确的“候选 → 验收 → 正式状态变更”边界：

- 候选默认无正式写入和外部发送权限，读取授权的快照或模拟数据。
- 先检查不可违反的硬约束，再按延迟、成本等软目标选优；软得分不能抵消硬约束失败。
- 选中候选输出待执行计划，绑定规则版本、预期状态版本、操作唯一编号与证据。
- 提交前核对最新权限与状态；状态改变时重新验证。使用适合该业务的事务、锁或条件写入来保护检查与写入。
- 若存在外部服务，明确哪些效果不能撤销、如何避免重复、如何核对结果不明的请求。
- 失败、冲突、无法判断或预算耗尽时拒绝自动提交，保留证据并停止或升级。

这里的“提交”是业务事实发生改变，不是 Git 的版本保存。把文件保存到 Git 不等于部署或修改用户业务状态。

## 一个并发反例

【建议】用虚构库存测试：两个候选都在“剩余 1 件”的快照下通过单独检查，不能据此让它们各卖 1 件。正式提交必须重新保护“库存不小于零”的条件，否则单元验收通过也会产生组合错误。

【已确认】数据库的可串行化隔离要求对特定冲突失败准备重试；这是具体机制的文档行为。[E04](../证据-Evidence/证据与参考-Evidence-and-References.zh-CN.md#e04)<br>
【不确定】这并不证明跨数据库、消息和外部服务的整体操作具有相同保证。

## 最小验证设计

【建议】比较 A“一个候选＋相同严格提交边界”和 B“多个隔离候选＋相同严格提交边界”，这样能识别多候选试错的额外价值。需要时再做验证前置程度的对照，不削弱任一组的实际权限控制。

注入：快照过期、并发争用、重复请求、外部调用超时、候选越权、测试缺漏、多个候选同错。所有外部服务先使用模拟端点，禁止实验产生实际交易或消息。

记录候选淘汰原因、验收漏检、正式状态违规、重复效果、延迟、总成本和人工升级。登记“未知结果”数量，不把超时自动记为成功或失败。

## 判断和停止

【建议】运行前约定次数、预算、合格质量及最小有意义收益。B 在同等质量下改善完整成本或错误控制才支持 H4；若开销或模拟偏差抵消收益，则缩小范围或放弃多候选。

任何沙箱逃逸或未经允许的正式效果立即停止。没有观测到错误只支持该次测试范围，不能宣称“绝对安全”。
